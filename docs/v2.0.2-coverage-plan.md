# v2.0.2 coverage plan

v2.0.2 continues from the immutable v2.0.1 release commit
`aba31e83f1f7f143596456eec36df81fc9c0f237`. The release tag, its 99
transcripts, and its evidence record are historical facts; v2.0.2 work lands
only in descendant changes. The runtime remains pure Go and supports exactly
`server_version` 208–225 unless a separately reviewed protocol decision
changes that range.

This plan turns the remaining coverage gaps into bounded promotion work. It
does not treat a typed broker refusal as positive service proof, and it does
not add public surface merely to mirror the official SDK.

## Evidence and disposition rules

A behavior is **promoted** only when all of the following exist in the same
vertical change:

1. a verifier-clean live raw capture from the correct role and negotiated
   version;
2. a sanitized raw-frame transcript or exact live vector with the full source
   capture hash;
3. a deterministic regression through the public API, or a direct production-
   decoder assertion when the callback has no independently useful public
   behavior;
4. updated catalog, coverage matrix, message ledger, and live tracker rows;
5. focused tests followed by the ordinary deterministic gate.

A behavior is **blocked** only by an exact observed condition such as an
entitlement, account type, market state, TWS-only interaction, or broker
rejection. Record the typed error and the request shape, but keep the row
distinct from positive proof. Timeouts and malformed results are failures
unless the scenario is specifically designed to prove that behavior.

A behavior may be **removed** only when it is a proven duplicate, the official
surface no longer exists, or it is outside the project charter. Removal must
name the reason in the matrix and delete the corresponding executable catalog
entry. Difficulty capturing a callback is not a removal reason.

Fault-injection tests may deterministically chunk, delay, truncate, corrupt, or
disconnect live-derived frames. They may not invent a successful broker reply.
SDK 10.48 is a conformance oracle only when a live request or callback shape is
ambiguous; live Gateway behavior remains authoritative.

## Non-negotiable safety boundaries

- `readonly-live` at `127.0.0.1:4001` is real-money and API-read-only.
- `paper-dev` at `127.0.0.1:4002`, or paper TWS at `127.0.0.1:7497`, is the
  only role allowed to place, replace, exercise, or cancel orders.
- The one authorized v2.0.1 AAPL regulatory snapshot has been consumed. Never
  call, batch, schedule, or retry that regulatory request again.
- Do not automate TWS or Gateway through GUI/CUA tooling. Manual `orderBound`
  evidence requires the user to create a paper-TWS order while the recorder is
  already armed.
- Do not mutate TWS/Gateway configuration. `TWS().Config` remains read-only.
- Before every paper campaign, require a `DU` managed account and capture open
  orders, positions, executions, and account values. Clear stale campaign
  orders, fence cleanup with `CurrentTime`, preserve unrelated positions, and
  flatten only the campaign delta.
- If paper cleanup becomes uncertain, stop admission, use global cancel only
  on paper, reconcile, and resume only from the recorded baseline.

## Work order

### 1. Session- and market-dependent evidence

Run both role doctors, export the catalog, and deduplicate scenario names
across selected batches before recording. Prioritize evidence whose result can
change with the trading session:

1. positive smart and venue market depth, including depth reroute;
2. real-time bars and tick-by-tick Last, AllLast, BidAsk, and MidPoint;
3. generic quote ticks, odd-lot fields, EFP, and delta-neutral validation;
4. historical keep-up updates, histograms, and all historical-tick families;
5. news bulletins and any market-dependent scanner variants;
6. bracket/OCA natural triggers, accepted combo/BAG orders, and multi-asset
   execution/completed-order echoes.

Record positive callbacks where the roles permit them. Exact codes 10089,
10092, 10187, 10276, 2188, account restrictions, and no-data market outcomes
remain useful blocker evidence, but they do not advance a positive row.

### 5. Finish order and option semantics

Order work should prefer already captured campaigns before another live order:

- promote accepted bracket and OCA natural-trigger lifecycles, including
  sibling cancellation;
- qualify a current option vertical and prove BAG acceptance, per-leg values,
  execution, completed-order observation, cancellation, and reconciliation;
- exercise nondefault scale, pegged, adjusted, condition, compliance, and
  allocation fields only where the paper account can echo them safely;
- cover stock, option, future, cash, and combo execution/completed-order tails
  without claiming unsupported asset classes;
- retry the `IncludeOvernight` false replacement only as a new paper campaign
  if broker conditions or the official client behavior materially change;
- seek terminal exercise or lapse evidence only with bounded quantities and a
  complete option-plus-underlying reconciliation plan.

Manual `orderBound` is a recorder coordination task, not an automation task:
arm the client-0 paper-TWS capture, ask the user to place and cancel one bounded
manual order, then verify the binding, open-order, cancellation, fence, and
baseline. If the user does not act, retain the blocker.

### 6. Fill public-behavior and asset-class gaps

After the existing queue is smaller, expand coverage where it materially
improves the facade:

- account/portfolio: meaningful `PnLSingle`, account-update timing, and
  `$LEDGER-` key behavior;
- history: keep-up cancellation, histogram empties, timezone boundaries, and
  all tick result variants;
- quotes: multi-asset contract shapes, EFP, option computation, delta-neutral,
  odd-lot, and contract-specific news callbacks;
- orders: filters, nondefault execution fields, meaningful bond yield and
  redemption values, deactivated orders, and advanced echoes;
- news, FA, WSH, and display groups: successful callbacks where the account is
  entitled, with exact blockers retained otherwise.

Do not add speculative public types for callbacks that remain internal,
operator-mutating, obsolete, or outside the socket-protocol charter.

## Change and verification cadence

Keep one vertical correction or promotion per `jj` change. A protocol-adjacent
description names the role, negotiated server version, capture/hash, and SDK
version when SDK evidence affected the decision. Pure planning, tooling, or
documentation changes do not pretend to carry live proof.

After each slice, run the narrow decoder/public replay tests and
`go test ./...`. Before pushing a development change, run:

```text
go mod tidy -diff
go mod verify
gofmt -l .
go build ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=386 go build ./...
golangci-lint run
go test -shuffle=on -count=1 ./...
go test -race -shuffle=on -count=1 ./...
./scripts/check-api.sh
./scripts/fuzz-all.sh --check
go run golang.org/x/vuln/cmd/govulncheck@v1.6.0 ./...
```

The default API check compares compatibility against the frozen v2.0.1
manifest and permits additions. Before a v2.0.2 release candidate is named,
generate and review `testdata/api/v2.0.2.api`, teach exact mode to select that
manifest for v2.0.2, and run the full timed fuzz campaign. Never update an old
manifest to make a check pass.

## v2.0.2 acceptance gate

v2.0.2 is release-ready only when all of these statements are true:

- every original candidate is promoted, remains explicitly blocked with
  current evidence, or is deliberately removed under the rules above;
- every registered decoder/layout pair is raw-frame-attested, or the release
  record names the remaining pair and exact external condition preventing a
  callback;
- every retained raw capture verifies and every transcript passes full-hash
  provenance validation;
- exact-version coverage exercises the relevant request or field boundary,
  not only handshake reachability;
- deterministic, shuffled, race, lint, vulnerability, 386, API, capture,
  provenance, and timed-fuzz gates pass on one exact candidate tree;
- safe live suites pass with only exact typed environmental skips;
- paper open orders, positions, executions, and fees reconcile to baseline;
- the regulatory snapshot was not repeated and no GUI/CUA automation was
  used;
- the v2.0.1 tag, manifest, transcripts, and release record are unchanged.

Tagging, pushing a release tag, and publishing a GitHub Release remain separate
explicit release actions after the candidate gate. Ordinary reviewed
descendant development may be pushed to `main` without altering v2.0.1.
